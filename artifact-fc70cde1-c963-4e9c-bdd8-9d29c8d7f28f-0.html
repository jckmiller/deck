The Core Decision

Enterprise cloud LLM vs. local LLM

☁️ Cloud (OpenAI, Anthropic, Azure)

  • Frontier quality, zero infrastructure to manage
  • Pay per token — scales with usage, no capex
  • Data leaves our perimeter (governed by contract/DPA)
  • Provider controls model, pricing, deprecation
  • Network dependency & per-call latency

🖥️ Local (self-hosted, open weights)

  • Data never leaves our hardware — privacy by design
  • Fixed cost after hardware; unlimited inference
  • Full control: model choice, versioning, fine-tuning
  • Works offline / air-gapped; no rate limits
  • We own ops, GPUs, and quality ceiling

The Engine

How a local LLM actually runs

A local model is just a large file of weights. Something has to load it into memory and do the math to turn tokens into tokens — that "something" is an inference engine.

The Engine · Deep Dive

llama.cpp — the foundation

An open-source C/C++ inference engine that runs LLMs efficiently on ordinary hardware. It underpins most of the tools in this deck.

GGUF format

A single portable file containing the model weights + metadata. Download one file, run it anywhere.

Quantization

Compresses weights (e.g. 16-bit → 4-bit) so big models fit on modest GPUs/RAM, trading a little accuracy for a lot of speed & savings.

CPU + GPU offload

Runs on plain CPUs, Apple Silicon, or NVIDIA GPUs — and can split a model across GPU and RAM when it won't fully fit.

The Wrappers

What is a "wrapper" — and why we need one

Raw llama.cpp is powerful but low-level. A wrapper sits on top to handle the parts we don't want to hand-roll:

📦 Model management

Find, download, version, and switch between models with one command.

🔌 Standard API

Exposes an OpenAI-compatible endpoint so our apps can talk to it without custom code.

🖥️ Interface

A GUI or CLI for chatting, testing prompts, and tuning parameters.

⚙️ Orchestration

Handles memory, concurrency, and serving multiple users or apps.

The Wrappers · Detail

What each one does well

🦙 Ollama

The "Docker for models." ollama run llama3 downloads and serves a model with one command, exposing a clean local API. Ideal as the backend our internal apps call.

🎛️ LM Studio

A friendly desktop app to browse, download, and chat with models, tune settings, and flip on a local server. Best for non-experts and rapid prototyping.

⚡ Unsloth

Two jobs: fine-tuning models on our own data 2–5× faster with far less GPU memory (LoRA/QLoRA), and fast GPU inference of the result.

Making It Ours

Two ways to specialize a model

📚 Give it context (retrieval)

  • Model stays unchanged; we feed it the right info at query time
  • Fast to set up, easy to update — just change the documents
  • Best for facts, policies, docs that change often

🎯 Fine-tune (Unsloth)

  • We actually retrain the model on our data/style
  • Bakes in tone, formats, domain behavior permanently
  • Best for consistent behavior & specialized tasks

Context · How

Giving models our knowledge: RAG

RAG = Retrieval-Augmented Generation. Instead of hoping the model "knows," we look up the answer in our documents and hand it to the model.

STEP 1

Index

Our docs are chunked & stored in a searchable vector database.

→
STEP 2

Retrieve

A question fetches the most relevant chunks.

→
STEP 3

Augment

Those chunks are added to the prompt as context.

→
STEP 4

Generate

The model answers, grounded in our real data.

📄 File uploads

Drop in a PDF/doc for one-off, in-conversation context.

🗂️ Filesystem access

Give the agent tools to read/search folders directly on our machines.

🔎 Vector search

The engine behind RAG for scalable, always-current knowledge.

Interaction · Agent Front-ends

Talking to models: OpenClaw & Hermes

Both are open-source (MIT) AI-assistant "harnesses" that run on our own hardware, plug into local or cloud models, and meet users in the chat apps they already use.

🦞 OpenClaw

An assistant that runs on your own devices and connects to Discord, Slack, Teams, Telegram, WhatsApp, iMessage & 20+ channels. State, memory, and credentials stay on our hardware; models & agent harnesses are swappable plugins. A local Gateway is the control plane; a 501(c)(3) foundation stewards it, no paid tier or lock-in.

☤ Hermes (Nous Research)

A self-improving agent with a built-in learning loop — it creates & refines skills from experience, searches its own past sessions, and models the user over time. Full terminal UI plus the same messaging platforms. Runs on a $5 VPS, a GPU cluster, or serverless. Use any model with hermes model — no lock-in.

Building Our Own

A wrapper & agent we control

Because these tools speak a common OpenAI-compatible API, we can build a thin layer that's entirely ours — and evolve it into a full agent.

🧱 Our own wrapper

  • Point our app at a local engine (Ollama/llama.cpp)
  • Add our system prompt, guardrails & logging
  • Wire in RAG over our internal documents
  • Same API means we can swap models freely

🤖 Our own agent

  • Start from OpenClaw or Hermes (both MIT, both extensible)
  • Add custom tools, skills & filesystem access
  • Fine-tune the model with Unsloth for our domain
  • Deploy on-prem — data never leaves the building

Recommended next step

Pilot: Ollama + a RAG index of one department's docs, fronted by Hermes or OpenClaw, on a single GPU workstation.

Measure

Quality, latency, and cost-per-query vs. our current cloud spend.

Decide

Scale the pilot, fine-tune, and formalize an internal agent platform.
